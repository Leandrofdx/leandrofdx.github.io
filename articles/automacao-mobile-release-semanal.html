Automação mobile que sobrevive a release semanal

Leitura ~13 min · Quality Engineering

Mobile castiga qualquer ilusão de estabilidade. Device lab, SO fragmentado, permissão de sistema, push, deep link, loja, binário assinado. O modo de falha de quem tenta “cobertura ampla” em release semanal é cruel: a farm inteira no PR, 2h de fila, 15% de flake, e na sexta o time desliga o job para conseguir publicar. A automação não morreu por falta de ferramenta — morreu por matriz irrealista e suíte que testa o framework em vez do produto.

Defini o desenho para release semanal em torno de uma frase: caminho feliz curto e implacável nos riscos de loja e dinheiro. Tudo que não cabe nisso ou vai para bateria profunda fora do caminho crítico, ou vira checklist exploratório consciente.

Se a suíte mobile precisa de novela para interpretar o vermelho, alguém está depurando Appium, device farm ou dado sujo — não o app. Estabilize a plataforma de teste antes de adicionar cenário.

Matriz de devices: realismo, não catálogo

Padronizei a matriz a partir de telemetria de uso + risco, não a partir do marketing do fabricante. Três faixas:

  1. Tier A — bloqueante de merge/RC: 2–4 perfis que cobrem a massa de usuários e os SO mínimos suportados. Ex.: Android popular da faixa média na versão mínima e na atual; iPhone correspondente à política de suporte. Aqui roda smoke.
  2. Tier B — release / diário: mais 3–6 perfis por participação de mercado, fabricantes com skin problemática conhecida, tablets se forem receita real.
  3. Tier C — amostral / campanha: dispositivos raros, SO beta, resoluções extremas. Fora do PR. Entram em janela agendada ou pré-evento.

Critério de entrada na matriz: ≥ X% de sessões ou histórico de incidente específico ou requisito de loja. Critério de saída: participação irrelevante + zero incidente em 90 dias + custo de manutenção alto. Matriz sem política de saída só cresce.

Fragmentação de SO

  • Android: testar “versão mínima suportada” e “N e N-1 atuais” costuma pagar mais que espalhar fino em oito APIs.
  • iOS: menos fragmentação de OEM, mais rigor de permissão e de review. Deep link, ATT, background modes — poucos testes, alta disciplina.
  • Skins (Samsung, Xiaomi etc.): entrar na matriz só com evidência (bug real ou % alto). Senão é superstição cara.

Estabilidade Appium: intenção, não pixel

Com Appium (ou camada sobre ele), o custo explode quando o teste descreve pixel e hierarquia frágil. Prefiro fluxo de negócio: login, busca, checkout, área logada. Detalhe visual fica para snapshot pontual, screenshot diff em tela estável, ou QA exploratório.

Práticas que reduzem drama

  • Seletores de acessibilidade / resource-id estáveis acordados com o time mobile no DoD das jornadas críticas — o paralelo do data-testid web.
  • Esperas por estado da app (elemento, idle, deep link aberto), não sleep longo como arquitetura.
  • Setup via deep link / API / flag para chegar rápido no ponto testado; UI completa só quando a navegação é o risco.
  • Sessão e reset: cada teste assume estado conhecido. App data clear ou usuário efêmero. Mobile flaky quase sempre é estado — biometria pendente, onboarding pela metade, permissão negada na run anterior.
  • Versão pinada de Appium, drivers e imagens de device no CI. “Latest” em farm compartilhada é fonte de regressão fantasma.
  • Logs + vídeo + hierarquia na falha como artefato obrigatório. Sem isso, o debug vira call de uma hora.

Farm paralela vs BrowserStack (e afins): tradeoffs

Não existe escolha moral — existe perfil de custo e controle.

  • Farm própria / emuladores controlados: melhor para smoke rápido, iteração de PR, determinismo relativo. Pior para diversidade real de OEM e redes. Emulador mente em performance, push e alguns sensores.
  • Device cloud (BrowserStack, etc.): melhor para matriz B/C e validação pré-release em hardware real. Pior em latência de sessão, preço por minuto, e falhas de infraestrutura que parecem falha de app. Exige retry classificado e orçamento explícito.
  • Híbrido (o que desenhei na maioria dos casos): PR e desenvolvimento em emulador/simulador + 1 device real barato; RC e release em cloud com Tier A/B; Tier C amostral semanal.

Métrica de decisão: custo por sinal acionável (não custo por minuto de device). Cloud barata que gera 20% de falso positivo é cara. Emulador “grátis” que deixa escapar bug de OEM em pagamento também é caro.

Flake budget e ownership

Defini orçamento de flake para a suíte bloqueante — por exemplo, < 2% dos runs em janela móvel de 14 dias. Acima disso, congelo novos cenários e abro war room técnica até voltar. Parece agressivo; é o único jeito de impedir que a release semanal normalize o amarelo.

  • Quarentena com taxonomia: timing / dado / device-infra / seletor / SO.
  • Falha de infra de cloud ≠ falha de produto. Contabilizar separado. Se a cloud oscila, o gate precisa de retry limitado + classificação, não de fé.
  • Dono por jornada (time do feature) + dono da plataforma mobile de teste (runners, Appium, integração cloud).

Smoke versus suíte profunda no ritmo semanal

Smoke (PR / candidate cedo) — 20–40 min paralelizado

  • Instala, abre, login (ou storage de sessão), uma jornada de receita, logout/área segura básica.
  • Tier A apenas.
  • Zero dependência de push real ou biometria real.

Profunda (RC / noite pré-release)

  • Pagamento, deep links críticos, upgrade a partir da versão anterior da loja, permissões, offline/online básico se for core.
  • Tier A + B.
  • Pode incluir cloud real.

Release semanal — ritual mínimo

  1. Smoke verde no binário candidato.
  2. Profunda na noite anterior ou janela fixa.
  3. Checklist curto do que deliberadamente não está automatizado (biometria, compra real, store listing).
  4. Critérios de go/no-go amarrados a risco, não a “% de testes verdes”.

Quando não automatizar UI mobile

  • Fluxo sob experimento de UX agressivo (muda toda sprint).
  • Biometria/FaceID em todo run — preferir seam de teste + 1 validação manual/release.
  • Captcha, antifraude real, compra com método de pagamento não sandboxável.
  • Animações e microinterações cosméticas.
  • Push end-to-end real em todo PR (caro e instável); validar contrato de payload + 1 teste amostral em profunda.
  • Qualquer cenário cujo custo de estabilizar > risco residual × frequência de release.

Documento o gap. Risco assumido com checklist de release é engenharia. Risco escondido porque “não deu para automatizar” é dívida com juros na sexta à noite.

Anti-padrões

  • Farm inteira em todo PR.
  • Matriz definida por catálogo de fabricante sem telemetria.
  • Teste que percorre o app inteiro para validar um botão.
  • Uma conta real de staging compartilhada entre jobs paralelos.
  • Ignorar falha de device cloud como “flake do Appium” sem classificar.
  • Medir sucesso por número de casos, não por escapes de loja/pagamento.
  • Atualizar Appium/drivers no mesmo dia do corte de release.
  • Automatizar biometria e captcha para completar a pirâmide no slide.

O que eu colocaria em produção na segunda

  1. Exportar top devices/SO dos últimos 30–60 dias e redesenhar Tier A/B/C em uma página.
  2. Cortar a suíte bloqueante para smoke de jornadas de receita + auth; mover o resto para job RC.
  3. Acordar resource-id / accessibility id estáveis com o time mobile nas telas do smoke.
  4. Separar métricas: falha de app vs falha de infra cloud/emulador.
  5. Instituir flake budget e congelamento de novos testes se estourar.
  6. Seed de usuário efêmero + reset de app data entre testes; matar conta compartilhada.
  7. Definir híbrido: emulador no PR, cloud no RC, com orçamento mensal em minutos.
  8. Publicar checklist do não-automatizado para o ritual de release semanal.

Release semanal sobrevive com suíte previsível, matriz honesta e orçamento de flake. Amplitude teatral na farm é o caminho mais curto para desligar qualidade na hora em que ela mais importa.

Antes do próximo release

Me pergunto só isto: a suíte avisaria a tempo se o login ou o pagamento quebrasse no device que importa — ou ela só ocupa minutos no CI? Se a resposta for a segunda, a matriz pode esperar.
