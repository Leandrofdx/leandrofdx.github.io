Avaliando LLM/RAG sem virar “prompt theatre”

Leitura ~12 min · Quality Engineering

Se Hit@k, rubrica ou faithfulness ainda estão nebulosos, destrinche antes em LLM e RAG sem jargão: o que você precisa entender antes de avaliar.

Demo com prompt caprichado impressiona stakeholder. Produção com alucinação, grounding fraco, vazamento de contexto e custo por request fora de controle destrói confiança. A tese de AI QA é o oposto do teatro: dataset versionado, métrica com baseline, gate no pipeline e amostragem humana. Sem isso, cada “melhoramos o prompt” é anedota irreprodutível.

O failure mode mais caro é julgar a resposta gerada quando a recuperação já falhou. O time debate temperatura e system prompt enquanto o chunk certo nunca entra no contexto. Segundo failure mode: trocar modelo/embedding toda semana sem repor baseline — você não sabe se melhorou ou se o juiz LLM ficou mais generoso.

Se retrieval está errado, score de geração é ruído. Separe os evals. Corrija a etapa culpada. Só então discuta prompt.

Framework: duas camadas, uma disciplina de baseline

Desenhei a avaliação de RAG em duas baterias independentes, mais uma de sistema ponta a ponta.

Retrieval (antes de gerar)

  • Hit rate / Recall@k — o documento ou passagem gold está no top-k?
  • MRR / nDCG — quando a ordem importa para o prompt.
  • Context precision/relevância — quantos chunks recuperados são de fato úteis (estilo RAGAS context_precision / context_relevancy).
  • Cobertura de intenção — queries de cauda longa e sinônimos do domínio, não só happy path.

Geração (com contexto controlado)

  • Fidelidade / groundedness — a resposta afirma só o que o contexto sustenta?
  • Answer relevancy — responde a pergunta pedida?
  • Completeness — omite restrição crítica (prazo, exclusão, dosagem, cláusula)?
  • Formato e tool use — JSON schema, citações, recusa quando não há evidência.

Sistema (RAG completo)

Só depois das duas camadas: pipeline real (retrieve → rerank → generate). Métricas compostas tipo faithfulness + answer_relevancy (família RAGAS), asserts programáticos (DeepEval-style) e suites declarativas (Promptfoo-style) no CI. O pensamento importa mais que a marca da lib: casos versionados, scores limiarizados, relatório diff contra baseline.

Playbook

1. Golden set versionado

Padronizei golden sets como artefato de engenharia, não planilha no Drive:

  • Repo ou dataset registry com tag (semver): inputs, contexto gold, resposta esperada ou rubrica, metadados (idioma, intent, risco).
  • Splits: regression (estável), exploratory (cresce), adversarial (red team).
  • PR de mudança de dataset exige diff e motivo — “achei melhor” não mergeia.
  • Tamanho honesto: 50–200 casos bem curados batem 5.000 sintéticos sem revisão.

2. LLM-as-a-judge com rubrica — e humano no loop

Juiz LLM escala, mas herda viés. Eu só uso com:

  1. Rubrica explícita (critérios, pesos, exemplos de score 1 vs 5).
  2. Mesmo modelo-juiz e prompt-juiz versionados no baseline.
  3. Amostragem humana periódica (ex.: 5–10%/semana ou todo release) com kappa/acordo mínimo; se divergir, recalibra rubrica.
  4. Asserts determinísticos onde der (regex, JSON schema, proibições de frase, presença de citation id) — juiz só no subjetivo.

3. Red team no pipeline, não em workshop

  • Prompt injection — instruções no documento recuperado e no input do usuário tentando override de system.
  • Jailbreak / exfiltração — pedidos de system prompt, chaves, dados de outros tenants.
  • PII — o sistema deve recusar ou mascarar; eval verifica vazamento em output e em logs enviados ao provedor.
  • Dados sensíveis no índice — chunk que não deveria estar searchable.

Esses casos entram no split adversarial e falham o job como qualquer regressão funcional. Workshop único sem gate é teatro de segurança.

4. Gates de custo e latência

Qualidade sem economia é release suicida em LLM. No mesmo pipeline de eval:

  • Tokens in/out médios e p95 por caso (e custo estimado por 1k requests).
  • Latência p95 retrieve, generate e end-to-end.
  • Teto por journey; regressão >X% contra baseline bloqueia merge ou exige waiver assinado.

Demo local com modelo menor e cache quente não é evidência. Gate roda na config de staging (modelo, região, concurrency).

5. Disciplina de baseline

Defini: toda mudança de prompt, modelo, embedding, chunking ou reranker gera run de eval completo; o relatório é diff vs última baseline tagged. Aceite só com:

  • Métricas primárias ≥ baseline (ou trade-off explícito documentado).
  • Nenhum caso P0 adversarial novo falhando.
  • Custo/latência dentro do orçamento.

“Melhorou na minha opinião” não é release criterion.

6. Privacidade no pipeline

  • Golden set sem PII real — sintetizar ou anonimizar com política clara.
  • Scan automatizado de PII em outputs e em payloads enviados a APIs de modelo.
  • Controles de retenção no provedor; opt-out de training onde existir.
  • Testes de isolamento multi-tenant no retrieve (não vazar chunk de tenant B).

7. Como pensar no estilo RAGAS / DeepEval / Promptfoo

Não importa qual lib você escolhe no trimestre — importa o desenho mental:

  • RAGAS-style — métricas decomponíveis (context recall, faithfulness, answer relevancy) que forçam a separar retrieval de geração.
  • DeepEval-style — asserts no código de teste (“a resposta deve citar X”, “não deve inventar Y”) rodando no pytest/CI como qualquer unit.
  • Promptfoo-style — suíte declarativa YAML/JSON com providers, prompts e assertions; bom para matrix de modelo × prompt × caso.

Eu combino: dataset versionado + asserts determinísticos no CI crítico + métricas decomponíveis no job de regressão + matrix só quando estou comparando mudanças de prompt/modelo de propósito. Matrix eterna em todo PR é custo sem sinal.

8. Falhas típicas de retrieval que o time culpa no LLM

Antes de “melhorar o prompt”, verifico:

  • Chunking que parte tabela/cláusula no meio — recall até sobe, fidelidade cai.
  • Embedding desatualizado após reindex parcial.
  • Filtros de metadados (tenant, produto, idioma) ausentes ou errados.
  • Top-k alto enchendo contexto de ruído; modelo “escolhe” o chunk errado.
  • Query do usuário ≠ query de retrieve (falta query rewrite / HyDE quando o domínio exige).

Cada item vira caso no golden de retrieval com documento gold explícito. Sem documento gold, você não tem eval de retrieve — tem opinião.

9. Release criterion mínimo para RAG

Defini um cartão de release que o PR precisa anexar (automatizado no relatório):

  1. Diff vs baseline tagged (métricas primárias).
  2. Lista de casos novos falhando (zero P0 adversarial).
  3. Custo e latência p95 dentro do orçamento.
  4. Amostragem humana do ciclo ainda válida (data) ou refeita neste release.
  5. Scan de PII/injection verde.

Se o time não consegue preencher o cartão, não há evidência — há demo.

Anti-padrões

  • Prompt theatre — demo ao vivo como prova de qualidade.
  • Um score único mágico — esconde falha de retrieval atrás de prosa fluente.
  • Juiz LLM sem amostragem humana — você otimiza para o juiz, não para o usuário.
  • Dataset estacionário por meses — produto mudou; eval mente.
  • Troca de modelo sem baseline — narrativa de upgrade sem evidência.
  • Red team só em slide — zero casos no CI.
  • Ignorar custo — qualidade “perfeita” a R$ por request inviável.
  • Avaliar só happy path em português formal — cauda longa, typo, mix de idiomas e tom agressivo quebram em prod.

Checklist de segunda

  1. Separe o último bug de “resposta errada”: foi miss de retrieval ou geração infiel? Abra o trace/chunks.
  2. Versionar o golden set atual (tag); proíba edição silenciosa na main sem PR.
  3. Rodar eval de retrieval@k e de faithfulness em isolation; publique os dois números no canal do time.
  4. Adicionar 10 casos adversariais (injection + PII) se ainda não existem; ligar no CI.
  5. Registrar baseline de custo/latência p95 na config de staging.
  6. Amostrar 20 outputs da semana para revisão humana contra a rubrica; anotar divergências com o juiz.
  7. Bloquear próximo “vamos trocar o modelo” sem job de diff contra a baseline tagged.

Demo bonita continua existindo. Eu só paro de confundir aplauso com release. Se não tem baseline e diff, para mim ainda é ensaio — e ensaio não vai para produção.
