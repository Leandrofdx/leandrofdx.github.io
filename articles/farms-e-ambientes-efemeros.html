Farms e ambientes efêmeros: custo vs confiança

Leitura ~12 min · Quality Engineering

Ambiente eterno compartilhado é fábrica de falso negativo e de falso positivo. Alguém sujou o dado, outra pipeline está no meio do migrate, a versão não é a do PR, o teste “flaky” na verdade é contenda. A tese: ambientes efêmeros — sobe, testa, derruba — devolvem previsibilidade ao sinal de qualidade. O custo de cloud é explícito; o custo do shared podre é incidente, retrabalho e desconfiança na esteira.

O failure mode oposto também existe: efêmero mal desenhado que leva 40 minutos para subir, seed frágil, teardown que esquece PVC/NAT/IP elástico, farm de devices ociosa queimando orçamento. O time desiste e volta a testar “no joelho” no staging sagrado. Plataforma de qualidade ruim não é a que custa — é a que ninguém usa porque o feedback não chega a tempo.

Métrica que importa: minutos até sinal confiável no PR. Não quantidade de machines no slide nem “prod-like” no discurso.

Framework: shared hell vs ephemeral cost

Defini a escolha de ambiente com quatro variáveis:

  1. Contenção — quantos times/pipelines batem no mesmo estado ao mesmo tempo.
  2. Mutabilidade — schema, feature flags e dados mudam por PR?
  3. Fidelidade necessária — precisa de dependência real (gateway de pagamento, IdP) ou double basta?
  4. TTL do sinal — quanto tempo o engenheiro espera antes de ignorar a esteira.

Alta contenção + alta mutabilidade → efêmero (ou pelo menos namespace isolado por PR). Baixa contenção + dados caros de produzir + dependências licenciadas → shared controlado pode ser racional. A decisão é econômica, não ideológica.

Matemática custo vs incidente

Coloco na mesma planilha:

  • Custo mensal de stacks efêmeras (compute, DB, egress, devices) × utilização média.
  • Horas-engenheiro/semana perdidas em “staging vermelho por causa dos outros” × custo interno.
  • Incidentes/quarter rastreáveis a “não testamos a combinação certa” × custo médio de incidente.

Quase sempre, com mais de um squad na mesma esteira, isolamento ganha. Quando o número não fecha, o problema costuma ser setup lento — otimize o path efêmero antes de voltar ao shared como solução padrão.

Playbook

1. Stack efêmera com Terraform / K8s

Padrão que desenhei para PR/CI:

  • Namespace (ou projeto) por pr_id / run_id com labels de dono e TTL.
  • Helm/Kustomize da app sob teste + dependências leves (DB, cache, broker) via chart ou containers de composição.
  • Terraform só no que for cloud de verdade (DNS temporário, bucket, fila gerenciada); estado remoto com lock e workspace por PR.
  • Imagens imutáveis tagueadas com git SHA — nunca latest.
  • Health gate: testes só começam após readiness real (não só pod Running).

Se o bootstrap passa de ~10–15 minutos sem necessidade física (migrate enorme, bake de ML), quebre o problema: snapshot de DB, schema pré-migrado, warm pool de nodes, cache de imagem no cluster.

2. Seed e isolamento de dados

  • Seed idempotente versionado no repo (fixtures + migrate), aplicado no create do ambiente.
  • Tenant/prefixo por run — mesmo shared DB só é aceitável com isolamento lógico forte e limpeza garantida.
  • Proibição de PII de prod no seed de teste; subset sintético ou anonimizado com job auditável.
  • Contratos de limpeza — delete por label/run_id no teardown; job órfão noturno como rede de segurança.

Dado compartilhado sem dono é a forma mais rápida de voltar ao hell — mesmo em cluster efêmero se o banco for único.

3. Test farms (browser, mobile, runners)

Farm só paga se a fila for gerenciada:

  • Prioridade por risco (main/release > PR; smoke > full suite).
  • Paralelismo com teto de custo e de contenção no SUT.
  • Cache de imagem/emulador; pool warm para devices/browsers quentes.
  • Autoscaling com scale-to-zero fora de horário se o negócio permitir.
  • Métricas: fila wait, ocupação, taxa de erro de infra vs erro de produto.

Farm ociosa é dinheiro queimado. Farm saturada é pipeline mentiroso (timeouts que parecem bug de app). Eu trato farm como produto interno: SLO de espera e budget mensal explícitos.

4. Quando shared ainda é OK

  • Homologação com parceiro externo que exige URL estável e allowlist de IP.
  • Hardware raro / device farm física limitada — com reserva e calendário, não faroeste.
  • Dados de referência caríssimos de regenerar, com API de reset por tenant e freeze de migrate em janela.
  • Exploratory longo de um único time, sem CI concorrente.

Shared OK tem: dono, janela de mudança, reset documentado, e CI que não depende dele para o sinal de PR (PR usa efêmero; shared é estágio seguinte).

5. Disciplina de teardown

Padronizei teardown como parte do contrato do job, não como “best effort”:

  1. finally / post-action sempre executa destroy — inclusive em cancelamento.
  2. TTL controller no cluster (ex.: namespace sem heartbeat por N horas morre).
  3. Janitor diário: lista recursos sem label válida ou com TTL vencido; alerta se custo órfão > limiar.
  4. Estado Terraform: workspace PR destruído; unlock de emergência runbookado.

Sem janitor, efêmero vira shared caro e invisível.

6. Camadas de fidelidade (não clone cego de prod)

Nem todo PR precisa do grafo inteiro. Desenhei três faixas:

  • PR slim — serviço sob mudança + doubles/contratos das dependências; feedback em minutos.
  • PR integrated — serviço + 2–3 dependências reais críticas no mesmo namespace; para mudanças de fronteira.
  • Nightly / release candidate — grafo mais largo ou shared controlado; pegar o que o slim não cobre.

“Prod-like” sem estratificar vira setup de uma hora para validar um rename. Fidelidade sobe com o risco da mudança, não com o ego da plataforma.

7. Dados: receitas que funcionam

Três padrões que uso conforme o domínio:

  1. Snapshot migrado — imagem de DB com schema + seed mínimo; clone por PR (rápido se o snapshot for enxuto).
  2. Migrate from empty + fixtures — mais lento no bootstrap, mais honesto com evolução de schema; bom quando migrate é o risco.
  3. Factory na API — testes criam dados via endpoints internos de test support (protegidos); teardown apaga por run_id.

Evito misturar os três no mesmo pipeline sem regra: cada job declara a receita. Mistura gera “funciona na minha farm”.

8. Contabilidade semanal da plataforma

Trato custo de ambiente como métrica de qualidade. Toda semana olho:

  • Custo de compute/DB de namespaces efêmeros vs número de PRs sinalizados.
  • Custo órfão recuperado pelo janitor (se cresce, teardown está furado).
  • % de falhas de CI classificadas como infra/ambiente.
  • Tempo de fila da farm vs SLO.

Se o custo sobe e o tempo até sinal não cai, a plataforma está só engordando. Ajuste paralelismo, TTL, slim vs integrated — não peça mais budget cego.

Anti-padrões

  • Staging único como gate de PR — contenção garantida.
  • Efêmero sem TTL — cloud bill surpresa.
  • Seed manual “pede pro fulano” — não escala; não é plataforma.
  • Prod dump no teste — risco legal e flakiness por lixo.
  • Farm sem métrica de fila — você só descobre saturação quando o release atrasa.
  • Destroy só no happy path — cancelamento de job deixa sangue no cluster.
  • Prod-like teatral — clona tudo, inclusive o que não afeta o risco do PR; setup de 1h.

Checklist de segunda

  1. Meça o p50/p95 de “minutos até primeiro sinal” nos PRs da semana.
  2. Conte quantos jobs falharam por ambiente sujo / colisão (não por assert de produto).
  3. Liste namespaces/workspaces órfãos >24h; some o custo estimado.
  4. Confirme que todo pipeline com create tem teardown em finally + janitor.
  5. Separe: o que no shared atual poderia ir para stack PR com seed sintético?
  6. Defina SLO de espera da farm e teto de paralelismo; publique no canal de engenharia.
  7. Se bootstrap >15 min: abra item de warm pool / snapshot — não peça “paciência” ao time.

Uma conta que eu faço de cabeça

Custo do ambiente ocioso versus custo da última falha “fantasma” que ninguém reproduziu. Quase sempre o shared barato era o item mais caro da planilha — só não estava na linha de cloud.
