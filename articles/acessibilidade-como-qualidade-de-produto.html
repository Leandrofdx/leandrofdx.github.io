Acessibilidade como qualidade de produto

Leitura ~12 min · Quality Engineering

Acessibilidade não é “feature social” opcional nem slide de compliance no fim do projeto. É qualidade de produto: se uma pessoa não consegue comprar, autenticar, ler o erro ou concluir o fluxo com teclado e leitor de tela, o sistema falhou — do mesmo jeito que falha com bug de pagamento ou p99 estourado.

Eu testo acessibilidade porque me importo com quem usa o produto em condições diferentes das minhas — e porque ignorei isso custa caro: exclusão, risco jurídico (LBI / WCAG em contratos públicos), retrabalho tardio e dívida de UI que a automação “feliz path” nunca vai pegar.

A11y madura não é score 100 no Lighthouse uma vez. É critério de release, regressão contínua e empatia operacional — teclado, contraste, nome acessível, foco e leitor de tela no caminho crítico.

O failure mode clássico

O time “passa no axe” no CI, celebra o badge e ninguém nunca navegou o checkout só com Tab. Ou pior: contrata auditoria pontual, gera PDF de 80 páginas, e zero item vira gate. Outro modo de falha: tratar acessibilidade como responsabilidade exclusiva de design — QA só “valida visual”. Resultado: botão sem nome, modal que prende foco, erro só em cor, formulário que o VoiceOver não anuncia.

Automação ajuda. Automação sozinha mente. Ferramentas pegam uma fatia (muitos problemas de nome, contraste estático, ARIA quebrada). Não substituem julgamento humano nem teste com tecnologia assistiva.

Framework: o que eu cobro em qualidade

Uso quatro camadas — baratas primeiro, caras quando o risco justifica.

1. Padrão e escopo

  • WCAG 2.2 como referência (AA como alvo mínimo de produto; AAA só onde o negócio exige).
  • Jornadas críticas — login, compra, agendamento, recuperação de senha, fluxos com dado sensível — não “todas as telas do design system de uma vez”.
  • Persona assistiva mínima — teclado only, leitor de tela (VoiceOver / NVDA), zoom 200%, contraste.

2. Shift-left no componente

  • Storybook / design system com regras de foco, label, estado disabled anunciável.
  • PR de componente novo sem aria-* inventado sem padrão — ARIA errada piora a experiência.
  • Checklist curto no code review: nome acessível, ordem de foco, contraste do estado de erro.

3. Automação no pipeline

  • axe-core (via Playwright, Cypress ou pa11y) nas rotas críticas a cada PR relevante.
  • Assersões de nome acessível e papéis (getByRole) — o teste já documenta como a UI deve ser percebida.
  • Lint de a11y em JSX/HTML quando o stack permite (eslint-plugin-jsx-a11y).
  • Gate com baseline: falhas novas bloqueiam; débito conhecido versionado, com dono e prazo — não “warn forever”.

4. Exploração assistiva (a camada que importa)

  • Script de teclado: Tab / Shift+Tab / Enter / Esc / setas onde fizer sentido.
  • Leitor de tela no fluxo feliz e no fluxo de erro.
  • Mobile: TalkBack / VoiceOver, tamanho de toque, orientação.
  • Cadência: release candidate ou mudança em jornada crítica — não só “quando sobrar tempo”.

Playbook: o que eu automatizo vs o que eu faço com as mãos

Automatizo com confiança relativa

  • Imagem sem texto alternativo (quando deveria ter).
  • Contraste de texto estático abaixo do limiar.
  • Controles sem nome acessível.
  • HTML inválido óbvio (label órfão, id duplicado que quebra associação).
  • Regressão de role/name em componentes versionados.

Não confio só na ferramenta

  • Ordem de foco em modal e drawer.
  • Mensagem de erro anunciada (live region) no tempo certo.
  • Captcha, drag-and-drop, canvas, mapa, player de mídia.
  • Conteúdo dinâmico de SPA que “passa no axe” e falha no leitor.
  • Linguagem clara e hierarquia de heading que faça sentido semântico.

Se o teste E2E só clica por CSS/XPath e nunca por papel/nome, a suíte treina o time a entregar UI que máquina encontra e pessoa usando leitor não.

Como eu encaixo no Quality Gate

Acessibilidade entra na mesma lógica de gate em camadas:

  1. Rápido — lint a11y + axe nas páginas tocadas pelo diff.
  2. Sob mudança — fluxos críticos com getByRole + smoke de teclado automatizado onde for estável.
  3. Caro — sessão assistiva humana / RC antes de release grande ou redesign.

Limiar: bloqueio para severidade alta em jornada irreversível (auth, pagamento, dados pessoais). Débito médio entra no backlog com ID e data — não some no Notion eterno.

Conversa com produto e engenharia

A11y vende mal como “faça o bem”. Vende melhor como risco:

  • Alcance — parte relevante da base não completa o fluxo.
  • Legal / edital — requisito explícito em governo e grandes contratos.
  • Qualidade estrutural — semântica boa melhora SEO, automação e manutenção.
  • Marca — exclusão vira história pública rápido.

Na forma de falar, evito tom de sermão. Prefiro evidência: “neste build o botão Confirmar não tem nome acessível; VoiceOver lê ‘botão’; impacto no checkout; correção é label/aria-label no componente X”.

Anti-padrões

  • Overlay mágico de acessibilidade como solução — raramente substitui HTML semântico e costuma quebrar mais.
  • Só contraste no Figma — e zero teste no produto renderizado.
  • ARIA em tudo — quando um botão nativo resolvia.
  • Score de Lighthouse como KPI único — fácil de gamear, frágil como verdade.
  • “Vamos deixar para depois do lançamento” — depois vira redesign.
  • Testar só happy path visual — erro e vazio são onde a11y mais falha.

Checklist de segunda

  • Mapear 3–5 jornadas críticas e o nível WCAG alvo (AA).
  • Ligar axe (ou equivalente) no CI nessas rotas, com baseline versionada.
  • Reescrever 1 smoke E2E para getByRole / nome acessível.
  • Rodar um fluxo só de teclado e anotar as três piores barreiras.
  • Abrir 1–3 issues com severidade, evidência e componente dono — sem manifesto genérico.
  • Combinar com design: tokens de contraste e estados de foco visíveis no DS.

Não escrevo sobre a11y por moda. Escrevo porque já vi fluxo “verde” no CI e inutilizável de teclado. Se o produto é para pessoas, isso não é extra — é o mesmo critério que uso para pagamento e PII. Só que aqui o prejuízo às vezes não aparece no dashboard.
